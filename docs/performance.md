# 性能与可依赖性验证

2026-10-12 在本机 Go 1.25、Linux amd64 下测量。这里记录的是内存和本机基准，不代表公网 Torrent 或 WAN 吞吐。基准源码保留在 `internal/engine/http_bench_test.go` 与 `internal/model/model_bench_test.go`。

## 已测量的改动

| 场景 | 改动前 | 改动后 | 解释 |
| --- | --- | --- | --- |
| 读取一个 8 MiB HTTP Range，三次结果的时间中位数 | 12.87 ms | 3.84 ms | 本地 HTTP 服务，省去缓冲区逐步扩容和复制 |
| 同一 Range 的稳态累计分配 | 约 41.8 MB/段 | 约 86–95 KB/段 | 每个 worker 另预分配并复用约 8 MiB 缓冲区，不包括在稳态每段分配中 |
| 1000 个文件 + 512 KiB 元信息的任务快照复制 | 约 7.8 ms | 约 0.23 ms | 用直接深拷贝替代 JSON/base64 往返；保留可变字段隔离 |
| 同一任务快照的累计分配 | 约 2.0–2.8 MB | 约 0.75 MB | 不再重复编码和解析元信息 |

默认四个 HTTP 分段 worker 的数据缓冲区约 32 MiB，随任务槽位数量线性增长。所有下载任务共享 HTTP 连接池；源站额度释放或调整时通过通知唤醒等待者，取消了 20 ms 轮询。探测、复查和下载结束不会清空池。已写入的数据仍按块同步和提交检查点；目前没有牺牲恢复边界来合并 fsync。

远端文件导出复用完成时已计算的 SHA-256 和文件时间戳，正常 HEAD/Range 请求不重新扫描大文件。时间戳或尺寸发生变化时要求重新验证。本机取回最终仍验证 SHA-256，避免把传输完成误认为数据正确。

下载重试只有一个层次，最多五次运行。分段失败后取消本次其他请求，再从已同步的数据块恢复；不会发生分段重试与任务重试相乘。

复现命令：

```sh
go test -tags nosqlite ./internal/engine -run '^$' -bench BenchmarkHTTPRange -benchtime=8x -count=3
go test -tags nosqlite ./internal/model -run '^$' -bench BenchmarkTaskCopy -benchtime=10x -count=3
```

结果会受到 CPU、内存、Go 版本、GC 与本机网络影响。吞吐数值只能用于这里的前后对比；无法据此保证远端达到相同速度。

## 验证范围

- 本地 HTTP：实际 Range 能力、强 ETag、分段并发、源变化、无可靠标识拒绝续传、截断响应、已有文件保护、校验失败、跨源认证 header 清理、瞬时错误后的检查点恢复。
- 本地 FTP：REST/SIZE/MDTM 能力与恢复，连接取消；单文件单流。
- 本地 Torrent peer：磁力元信息、文件选择、跨文件分片、空文件和损坏后的分片恢复。
- 服务：优先级、任务额度、修订冲突、幂等键、等待取消不影响任务、状态恢复、数据库写入失败不应用暂停意图、不报告未持久化的完成。
- 远端：TLS 证书信任、错误令牌、非回环 HTTP 配置拒绝、路径限制、取回 SHA-256、取回取消与续传、文件变化拒绝、真实独立 daemon 进程的 HTTPS 下载与取回。
- 可选节点：两台独立 daemon 的负载选择、客户端重启后的归属保持、并发提交去重、丢失回复后的重试去重、已分配节点离线或移除时不重投、MCP 调度与取回、本地 torrent 元信息上传。
- `go test -race` 与 `go vet`；测试不依赖公共 Torrent swarm。

真实公网 swarm、特定 FTP 服务、多日持续运行和真实多机 WAN 吞吐尚未测量。要调整块大小、任务额度或引入跨节点分片，应先记录可重现的来源、文件大小、磁盘与网络条件，并比较吞吐、资源占用和失败恢复成本。
